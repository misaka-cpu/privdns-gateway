# 跨版本升级入口: 从一份经核验的副本运行 `pdg update --to`

旧版 CLI 不认识 `--to`。所以**不能**只写一句"运行 `pdg update --to <tag>`" —— 机器上那个
`/usr/local/bin/pdg` 还是旧的, 它会把 `--to` 当成无关参数忽略掉, 照旧装最新发布。

正确形态只有一种: **从一份经过身份核验的完整副本里直接运行新版脚本**。

```bash
sudo bash <入口副本>/deploy/bot/pdg.sh update --to <版本tag>
```

入口副本只提供 `pdg.sh` 这一个本体。被更新的对象**始终**是现役受管仓库
`/opt/privdns-gateway`: 方向判断、`pre_sha`、快照、`reset`、回滚全部作用在它上面, 与入口
放在哪个目录无关。运行时屏幕上会把这两件事分两行打出来, 事后可据此判断当时跑的是谁。

---

## 一、完整调用流程: 一段脚本, 每一步都必须自己成功

下面这段是**唯一**的调用形态。它必须**整段存成一个文件跑** —— 三个变量、每一步的退出码
检查、以及"失败就停"的控制流都在同一个执行上下文里。拆成几段分别粘进终端的话, 变量会在
段与段之间丢掉, 前一步的失败也拦不住后一步。

判据只有一条: **取得副本、取件、解析目标、检出、读回实际 HEAD、查询工作区状态 —— 六步
各自都要成功, 且实际 HEAD 必须等于带外拿到的完整预期 SHA。任何一步不成立, 都不进入提权
执行。** 这里不看"最后一条命令的退出码", 也不拿"输出是空的"当成"查询成功了"。

```bash
#!/usr/bin/env bash
# --- pdg-bridge-entry-flow: BEGIN (验收测试按这两行标记抽取本段原文执行) ---
# shellcheck shell=bash
set -u

# ① 带外取得的预期身份。必须来自受信交付记录, 不能从等会儿下载的那个包里读。
TAG="${TAG:-<在此填入版本tag>}"
WANT="${WANT:-<在此填入交付记录里的完整提交SHA>}"
ENTRY="${ENTRY:-$HOME/pdg-entry}"
# 取件来源。默认就是官方 HTTPS 仓库; 验收测试会把它指向隔离环境里的自有仓库,
# 那是**模型**, 不是官方发布路径。
SRC="${SRC:-https://github.com/misaka-cpu/privdns-gateway.git}"

stop(){ echo "❌ $1 —— 停止, 不进入提权执行"; exit 1; }
case "$TAG$WANT" in *'<'*) stop "TAG / WANT 还是占位符, 先填成真值";; esac
case "$WANT" in [0-9a-f]*) [ "${#WANT}" = 40 ] || stop "WANT 不是 40 位完整 SHA";;
                        *) stop "WANT 不是 40 位完整 SHA";; esac

# ② 取得副本(此时还不提权)
[ -e "$ENTRY" ] && stop "$ENTRY 已存在 —— 换个空目录, 不在旧副本上就地覆盖"
git clone -q --no-checkout "$SRC" "$ENTRY" || stop "取得副本失败"
# ③ 取件
git -C "$ENTRY" fetch -q --tags origin || stop "取件失败"
# ④ 解析目标 tag(`^{commit}` 不能省: 附注 tag 自己的哈希不是它指向的提交)
GOT="$(git -C "$ENTRY" rev-parse -q --verify "refs/tags/$TAG^{commit}")" \
  || stop "解析目标失败: $TAG 在取件到的仓库里不存在"
[ "$GOT" = "$WANT" ] || stop "身份不符: 期望 $WANT, 实得 $GOT"
# ⑤ 检出。**必须看它自己的退出码** —— 检出失败时工作区照样可以是"干净"的,
#    那时后面几步全都成立, 却跑的是另一个提交(甚至是旧入口)。
git -C "$ENTRY" checkout -q --detach "$WANT" || stop "检出失败(index.lock 占用 / 磁盘 / 权限)"
# ⑥ 读回**实际** HEAD 再比一次。④ 比的是"tag 指向谁", 这里比的是"我现在到底站在哪"。
HEAD_SHA="$(git -C "$ENTRY" rev-parse -q --verify 'HEAD^{commit}')" || stop "读不回实际 HEAD"
[ "$HEAD_SHA" = "$WANT" ] || stop "实际 HEAD 是 $HEAD_SHA, 不是预期的 $WANT"
# ⑦ 查询工作区状态。先确认**查询本身成功**, 再看结果是不是空 ——
#    查询失败时 stdout 也是空的, 拿"空输出"当"干净"等于把失败读成通过。
if ! ST="$(git -C "$ENTRY" status --porcelain)"; then stop "工作区状态查询失败"; fi
[ -z "$ST" ] || stop "工作区不干净: $(printf '%s' "$ST" | head -3 | tr '\n' ';')"

echo "✅ 身份核对通过: $TAG → $WANT(实际 HEAD 一致, 工作区干净)"

# ⑧ 先预览。预览非零就到此为止, **不进入正式更新**。
sudo bash "$ENTRY/deploy/bot/pdg.sh" update --dry-run --to "$TAG" \
  || stop "预览失败(锁忙 / 取件不通 / 方向被拒)"
# ⑨ 正式执行
sudo bash "$ENTRY/deploy/bot/pdg.sh" update --to "$TAG"
# --- pdg-bridge-entry-flow: END ---
```

核验失败时**停止**: 不重试、不换源、不"先跑起来再说"。

### 关于这段脚本的两个提醒

* `sudo` 只出现在 ⑧⑨ 两行。前面七步全部以普通用户身份完成 —— **先核对身份, 再提权**。
* 脚本用 `set -u` 而**不用** `set -e`: 每一步的失败都由它自己那句 `|| stop` 明确接住,
  这样失败时能说出是哪一步、为什么。靠 `set -e` 兜底会让"哪一步断的"变成猜。

## 二、信任边界(别把它当成它不是的东西)

* 完整提交 SHA 的作用是**冻结对象**与**检查内容一致性**: 它能保证"我拿到的确实是交付
  记录里说的那一棵树"。它**不是**独立签名认证 —— 没有第三方在为这个 SHA 背书。
* 同一个下载包里自带的摘要文件**不算带外认证**。预期 SHA 必须另路取得。
* 传输安全靠的是 HTTPS 与 GitHub 的证书链。本轮**没有**建立新的签名体系, 也**没有**正式
  分发这个入口。

## 三、明确不做的事

* **不通过 `install.sh` 绕过已有部署门**。`install.sh` 是首次安装路径, 它有自己的前置检查;
  用它来"顺便升级"等于从侧门进来, 把 update 的快照、方向判断、回滚全部跳过。
* **不使用任何 FORCE / SKIP / BYPASS 开关**。`--to` 只收窄目标, 不放宽任何门:
  ahead(机器上跑着未发布的提交)与 diverged(分叉)照样拒绝, 它不兼作降级工具。
* **不在快照之前覆盖现役 CLI**。安装新脚本发生在建快照之后; 快照失败即中止, 不在无法
  回滚的前提下继续。
* **入口副本不是受管仓库**, 升级过程中不会去写它。

## 四、`--to` 的取值规则

| 写法 | 行为 |
|---|---|
| 省略 `--to` | 默认契约不变: 装仓库里最高的 `v*` tag |
| `--to v1.11.15` / `--to=v1.11.15` | 钉在这一版 |
| `--to`(后面没跟值) | 报错。取件之前就拒 |
| `--to ""` / `--to=` | 报错。**显式空值不等于省略**, 不会悄悄改装最新发布 |
| `--to <非 tag 形态>` | 报错。取值会拼进 `refs/tags/`, 只接受 `v` 开头的版本 tag 名 |

目标在方向门**之前**解析并固定成一个提交, 正式执行路径上每次用到它之前会复核 tag 没被挪走,
不会成功短路到另一个对象。**处置分两种, 别混称"停止并回滚"**:

* 复核发生在**建快照之前**(方向门那一处)→ 直接停止: 未建快照、未 reset、未重启服务,
  也就**没有回滚这回事**;
* 复核发生在**建快照之后**(真正要 reset 那一处)→ 停止**并**回滚到更新前快照。

另外, `--dry-run` 与正式执行**不是逐步走同一条复核路径**: 预览只做一次解析并把目标打印出来,
它不跑上面那两处复核(它也没有快照可回滚)。两者共用的是选版契约, 不是同一串步骤。

目标不存在、取件失败、关系判不出来 —— 三种情形的处置都是**停止**, 而且都不会改装最新发布。

### 预览与执行的关系: 说到哪儿为止

预览与执行共用同一套**选版契约**(同一处参数解析、同一个关系判据、同一条固定+复核的路径)。
**但共用契约不等于两次调用被绑在同一个提交上。**

* 预览是一次独立调用, 执行是另一次独立调用。**每次调用各自解析一遍目标**。
* "固定一次 + 每次用前复核"的保证**只在单次执行内成立**: 那一次里目标被钉成一个提交,
  中途 tag 被挪走就停(在快照前是直接停, 在快照后是停并回滚, 见上一节)。
* 所以**不能**承诺"预览之后不论对象怎么变, 执行仍必然装上预览时看到的那个 SHA"。
  这条边界保留: **两次调用之间没有任何绑定**。
* 但也**不要反过来猜**"上游一重打 tag, 下一次就会装上新对象"。取件用的是
  `git fetch --tags origin main`, **没有 `--force`**, 于是要看现役仓库里有没有同名 tag:
  * 现役仓库**已有**该 tag(升过一次就有)→ git 拒绝覆盖
    (`! [rejected] … (would clobber existing tag)`)并且**整条 fetch 返回非零**,
    于是钉版解析报"取件失败 → 无法确认钉版目标"并停止。既不会装新对象, 也不会装旧对象;
  * 现役仓库**还没有**该 tag → 取件拿到的就是新对象, 这一次会按新对象走。
  两种都可能, 取决于现场, 所以事前无从断言 —— 这正是"没有跨调用绑定"的具体样子。
* 执行输出里的 `钉版目标已贯穿到实际安装: <tag> → <提交>` 只是**事后核对**用的:
  它让你在事情发生**之后**知道装上去的是哪个对象, 并**不构成事前绑定**, 也拦不住
  两次调用之间的变化。

另外, 有两个"身份"不要混为一谈:

* **入口副本的身份** —— 上面第 ①–⑦ 步核的那个 `WANT`, 说的是"我正在运行的这份 `pdg.sh`
  是哪一版";
* **安装目标的身份** —— `--to` 在**现役仓库**里解析出来的那个提交, 说的是"要把
  `/opt/privdns-gateway` 装成哪一版"。

两者用的往往是同一个 tag 名, 但它们是在**两个不同的仓库**里各自解析的, 各自成立或失败。
入口副本核验通过, 不代表现役仓库里那个 tag 也指向同一个提交。

## 五、`--dry-run` 不是完全只读(行为变化, 如实登记)

`--dry-run` 不装任何东西、不迁移、不改生产文件, 但它为了知道"最新/目标是哪一版"要
`git fetch --tags`, 那会写现役仓库的 `FETCH_HEAD` 与 `refs/tags/` —— 与执行路径写的是
同一批 git 元数据。

因此在这一版的 `pdg.sh` 里, **`--dry-run` 也持有那把既有的更新锁**(`/run/privdns-gateway.lock`,
与执行路径同一把, 不是第二把)。取锁在第一次可能写现役仓库的取件之前; 锁被别的 pdg 操作
占着时, 预览会**立即拒绝并且一次都不取件**:

```
⛔ 已有 pdg 操作在运行, 请稍后再试 (锁: /run/privdns-gateway.lock)
```
