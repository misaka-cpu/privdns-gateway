# 路线图与技术债务边界

这份文件回答两个问题:**现在做到哪了**,以及**代码里那些看着"没做完"的东西为什么还在**。

第二个问题尤其要紧。仓库里还有约一百多处 sing-box 相关引用,不看这份文件的人会把它当成
"5.3 没做完"。它不是 —— 那是有意保留的兼容层,清理时机与前提写在下面。

### 第一阶段的完成判据

1. **无效配置进不了生产**:成功 / 候选校验失败 / 服务失败 / 回滚失败四条路径都有真实行为
   测试;所有会写受管配置的入口都走 `pdgtx`,没有例外留在锁外。
2. **配置损坏时能从私网救援入口恢复**:救援平面不依赖 mihomo / mosdns / 公网 DNS,
   socket 激活独立,来源限制在应用层按内核 peer 地址判定(防火墙被清空也拦得住)。
3. **至少保留最近 10 份快照,并能查到变更来源**:保留策略有真跑验证(生成 12 份只留 10 份);
   每份带 `snapshot.json`,记 `source`/`op`/时间/版本。
4. **sing-box 迁移失败时旧内核继续可用**:有真实故障注入,不是读源码。
5. **新安装只走 mihomo,WLOC / Bot / doctor 不退化**:两个平台各自的干净安装沙箱都验过,
   Android 不装 iOS 模块,iOS 具备描述文件与 WLOC 所需模块。

## v2.0 清理候选:sing-box 兼容层

### 现状

- **v1.6.0 起本项目不再安装或启动 sing-box 运行时。** 新装机器上没有 sing-box 二进制,
  也没有 `sing-box.service`。唯一的流量内核是 mihomo。
- `/etc/sing-box/config.json` **仍然存在,但它已经不是 sing-box 的配置**,而是本项目的
  **数据模型**(出口、分流规则、final、面板设置)。mihomo 的运行配置由它渲染而来
  (`deploy/bot/sb2mihomo.py` → `/etc/mihomo/config.yaml`)。路径名是历史包袱,内容不是。

### 为什么这些还留着

| 保留项 | 为什么现在还不能删 |
|---|---|
| `lib/singbox.sh`(归属判定) | 老机器上可能有**第三方**装的 sing-box。卸载 / `--purge` / 迁移都必须能认出"这一份不是我们装的"并原样保留。删掉判据 = 有概率删别人的服务。 |
| `migrate_drop_singbox` 及相关迁移 | 仍有从 v1.5.x 及更早直接升上来的机器。删掉迁移 = 那些机器升级后同时躺着两个内核。 |
| 跨版本快照 / 回滚里的 sing-box 条目 | 快照要能回滚到**更旧的版本**。快照清单里少了 `usr/local/bin/sing-box` 与 `sing-box.service`,跨版本回滚就会把旧机器恢复成缺内核的半套状态。 |
| `/etc/sing-box/` 这个路径本身 | 它是数据模型的现居地。改路径要同时迁移:数据模型读写、备份成员白名单、恢复映射、快照候选集、越界守卫前缀、全部相关测试与文档。 |

### 清理前必须同步完成的事(缺一不可)

1. 数据模型迁出 `/etc/sing-box/`,并为老机器提供一次性迁移;
2. 备份 / 恢复的成员白名单与目标映射同步改名,且保证**旧备份包仍能恢复**;
3. 快照候选集与回滚越界守卫的前缀同步更新,跨版本回滚矩阵重跑;
4. 第三方 sing-box 的归属保护要么保留、要么给出等价替代 —— 不能直接消失;
5. 相关测试与文档一并改,不留"文档说没有了、代码里还在"的夹生状态。

在这五项之前,**不要**批量改写历史引用,也不要动历史 CHANGELOG、测试夹具和旧版说明 ——
那些是过去版本的事实记录,改了会让跨版本排障失去参照。
